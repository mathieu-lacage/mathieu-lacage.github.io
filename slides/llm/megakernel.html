Linear Layer

96 tasks on 96 SMs

Qwen3-1.7B's gate + up projection at decode, batch 8, as Mirage's `demo/qwen3/demo.py` runs it on a B200: C (12288 × 8) = A (12288 × 2048) · B (2048 × 8). A = the gate and up weights side by side (2 × 6144 rows), B = the 8 tokens after the RMSNorm, C = the input of SiLU-mul. M is drawn 2.5 × too short: to scale, a task would be a 7.5 px row. **Step 0.** A and C are cut in 96 blocks of 128 rows: one task each (`grid_dim = 96`, so each task's `OUTPUT_SIZE` is exactly one `MMA_M = 128` tile). B is not cut: every task reads all of it. **Step 1.** The B200 runs 128 workers, so all 96 tasks start at about the same time, each on its own SM. Each TMA warp issues its first 8 strips of A and B (faint blue): 96 SMEM rings fill at once; the first strips land and go to the tensor cores (gold). **Step 2 (auto-plays).** The 96 fronts sweep K together, each at its own pace (start offset, HBM contention). Each task streams its own 128 rows of A from HBM (512 KB; 50 MB for the layer, in bf16): that is what makes them memory-bound. All 96 read the whole of B, but B is only 32 KB and stays in L2. Each C block warms up as its TMEM accumulator fills, then turns solid gold when its epilogue stores it, without waiting for the other tasks. The layer is done when the slowest task is. One task: read from GMEM, MMA into TMEM

Source: Mirage persistent kernel, `tasks/blackwell/linear_sm100_mpk.cuh`. Task 5 of Qwen3-1.7B's gate + up computes 128 output features: C (128 × 8) = A (128 × 2048) · B (2048 × 8), K cut into 32 strips of 64. **Warp roles.** Warp 5 is the TMA producer, warp 4 the MMA issuer, warps 0–3 the epilogue. **The ring.** 8 SMEM slots (`NUM_AB_STAGE`), each holding A strip k (128 × 64, 16 KB) and B strip k (64 × 8). `smem_wr_buffer` and `smem_rd_buffer` are two cursors into the same ring, both equal to k % 8. Per slot, two mbarriers: `ab_full` (completed by the TMA's transaction bytes) and `ab_empty` (signalled by the MMA with `umma_arrive` once its 4 MMAs are done). **The MMAs.** 4 × `tcgen05.mma` per strip (`k_block` 0…3), each (128 × 16) · (16 × 8), read from SMEM in place through descriptors and added directly into the TMEM accumulator: 128 MMAs for the task. There is no per-strip partial: `ScaleOut::Zero` only on the very first MMA. **Memory-bound.** At decode batch sizes the MMA always waits on the next `ab_full`: 7 of the 8 slots are in flight at any time, the faint blue window in A and B. **Next slide.** Once all 32 strips are in, C holds the finished 128 × 8 block in TMEM.

One task: write back to GMEM

Warps 0–3, the epilogue, take over once all 32 strips are in. C, as it ends the previous slide, is magnified on the right: the TMEM accumulator, 128 lanes × 16 columns (8 of them padding: the tensor core needs N a multiple of 16 at M = 128). Every buffer after it is drawn the same way, features × tokens. 1. `acc_full`, then `tcgen05.ld`: warp w can only reach lanes 32w…32w+31, so each warp copies its own band; thread t gets row t in `tTR_rAcc`, 16 fp32 registers (64 B). Then `acc_empty`: TMEM is free. 2. fp32 → bf16 into a second register tensor, `tCrC`: 16 bf16 per thread (32 B, packed two per register). Gate + up has no bias or residual (the plain `linear_sm100` task). 3. `st.shared`: thread t writes its row into the SMEM C stage, a 128 × 16 bf16 tile (4 KB). 4. Fence + named barrier, then one thread of warp 0 issues the TMA store of the 8 real columns: task 5's 128 rows of out. In memory out is token-major (8 × 12288), so the store writes 8 runs of 256 B, 24 576 B apart; the SMEM tile is already laid out for it (`sC` stride (128, 1)). One tile per task, so one of the 2 TMEM stages (`NUM_ACC_STAGE`) and one of the 4 SMEM C stages (`NUM_C_STAGE`) are used. They matter for multi-tile tasks: the LM head runs 10 tiles per task, the MMA filling one TMEM stage while the epilogue drains the other, and up to 3 TMA stores in flight while the next tile is written to SMEM.

Paged Attention Layer

Paged attention

Decode « ␣of »: q5, k5, v5 as before. Keys and values 1–4 are in the cache

The cache is a pool of pages, 2 tokens each, shared by all the requests

A page table per request: tokens 1–2 are in page 5, tokens 3–4 in page 2

KT: columns 1–4 are gathered from pages 5 and 2, through the table

V: rows 1–4 come from the same pages

q5·KT, softmax, z5, o5: unchanged. The math does not see the pages

Page 2 is full: the free page 7 is added to the table, and k5, v5 go to its first slot

A request takes pages one at a time as it grows, and gives them back when it ends

The layout of « Decode » (inference deck), same coordinates and colours, for « ␣of » (n = 5). The only change: the « KV cache · this block and head » box becomes a pool of fixed-size pages (vLLM's PagedAttention). Without pages, each request reserves a contiguous cache for its maximum length up front; most of it stays empty, and the holes left by finished requests fragment memory. With pages, a request holds ⌈n / page size⌉ pages, wherever they are, and the page table turns a token position into (page, slot): page = table[pos / page_size], slot = pos % page_size. 2 tokens per page for the picture. In MPK: `--page-size`, 4096 by default. The page tables are `paged_kv_indices` (+ `paged_kv_indptr`, `paged_kv_last_page_len`), filled by the schedulers in `prepare_next_batch`, which also hands out and frees the pages. One page index is valid in every layer: each layer has its own k_cache, v_cache tensors of shape [num_pages, page_size, 8 KV heads, 128], indexed the same way. The append of k₅, v₅ is done by the attention task itself (next slide).

One request, one task per head

Request 2 at decode: 1 new token, 1024 keys of context, one layer of Qwen3-1.7B (16 query heads, 8 KV heads, d_h = 128). **attn_in** is the QKV linear's output: one row of 4096 per token. `shuffle_tensors` orders the QKV weights by KV head at build time, so the row is 8 groups of [Q 2h | Q 2h + 1 | K h | V h], and each task's inputs are one contiguous 512-value run of it. **One task per KV head** (`grid_dim = (R, 8, 1)`): task (r2, KV h) holds query heads 2h and 2h + 1 (GQA), so its 2 rows of Q meet the same Kᵀ_h and V_h, which it streams from the KV cache once for both. The new token's key and value come from attn_in (and are appended to the cache); the 1023 others from the request's pages. Physically the cache stores all 8 KV heads of a token side by side: each task reads its 128 of every 1024. Each query head's row of A (1 × 1024) fills as the keys stream; at decode there is no mask (the new token sees every past key: the last row of the causal triangle). O = Σ P·V / Σ P over the keys seen so far: inside the task it is an accumulator in registers, divided by the sum at the end. The scores and values are made up; the 8 tasks share nothing and run in parallel on 8 SMs.

Softmax: textbook vs online

One query head, 8 keys, made-up scores (the running max changes at keys 0, 2 and 4); every number on the slide is computed from them. **Textbook**: needs the whole row: max(S), then P = exp(S − max(S)) (subtracting the max keeps every P ≤ 1: no overflow in exp), then ΣP, then A = P / ΣP. **Online**: what the attention task does as it streams its keys from the KV cache. It keeps only two numbers per query head, the max of the scores seen so far and the sum of their P. When a key raises the max, every P computed so far, and ΣP, used the old one: they are all too large by exp(new − old), so they are multiplied by rescale = exp(old − new). At the end P / ΣP is exactly the textbook A, after one pass over the keys. (In the code: `m_local`, `d`, `rescale`; O is rescaled the same way, see the next slide.) This is the online softmax of FlashAttention (Milakov & Gimelshein 2018).

One request, one task per head: S, P, d

The previous slide, with what each query head keeps while its keys stream: the online softmax. Per key, S = q · kᵀ / √d_h (blue: the score). The task never holds the whole row: it keeps the running max m and P = exp(S − m) (gold). When a later key beats m, every P so far shrinks by exp(m_old − m_new), and so does the running sum d = Σ P (the number): that is the rescale in the code (`rescale[m]`, `d[m] *= rescale`, `o *= rescale`). O is accumulated the same way, Σ P · V, in registers, and divided by d once, at the end (here: drawn only when the task has seen all its keys). Scores made up as on the previous slide (a sink at key 0, recent keys, a few peaks); d's values follow from them. In MPK each warp keeps its own m, d, O over its 16 keys of every tile; the 4 are merged at the end (« merge » slide).

Accumulate from GMEM into registers

The attention task's counterpart of the linear task's ring slide. Source: `attention_sm100.cuh`. No TMA and no producer warp: the 4 warps (128 threads) issue the copies themselves, `load_smem` = `cp.async` 16 B per thread (`common/copy_sm80.cuh`), then compute. - **Q**, once: the task's rows of attn_in, its 2 query heads stacked token by token (`dst_row = src_row * NUM_QO_PER_KV + head`), into a 16-row tile (`MAX_TOKENS × 2` rounded up to an m16 MMA). RMSNorm (`q_norm`) and RoPE run in SMEM, on the first tile. - **K and V**, 64 keys (`KV_TILE_SIZE`) at a time, two buffers (`k_buffer_smem` / `k_smem`, same for V). A tile is 64 slots of one page (`PAGE_SIZE % KV_TILE_SIZE == 0`): `page_indices[pos / PAGE_SIZE]`, row `page · PAGE_STRIDE + pos % PAGE_SIZE`, KV head 5's 128 columns. Before computing tile t the threads issue tile t + 1 and `cp_async_wait<1>()`: tile t landed, t + 1 still in flight. - **The new key** (the last `num_tokens` positions) comes from attn_in, not from the cache: same loop, other source. After K's RMSNorm + RoPE, the new K and V rows are stored from SMEM to their page slot (page 0, slot 255 here: allocated by `prepare_next_batch` before the iteration). - **The warps** read their 16 keys of the tile through `ldmatrix` into registers, `mma.sync` into fp32 fragments: S_w, then O_w += P_w V_w. Nothing goes to TMEM. Page size 256 for the picture (`--page-size 256`); the pool shows 12 pages, r2 owns 6, 2, 9, 0. Bottom right: the same work as matrices (request 2's 16 query heads; this task's rows are heads 10 and 11).

Merge from registers into GMEM

The end of task (r2, KV 5), `attention_sm100.cuh` after the KV loop. Each warp ends the loop with a partial per Q head: its max(S), its ΣP and its O_w = Σ P·V (128 fp32), over its quarter of the keys. **Spill**: every thread writes its fragments to SMEM (`s_m_buffer`, `s_d_buffer`, `s_o_buffer`, one m16 tile at a time), then a block-wide barrier. No other warp joins: the same 4 warps now merge. **Merge**: `for (elem_idx = threadIdx.x; …; elem_idx += 128)`, row = elem / 128, col = elem % 128. Thread t takes column t of both rows (Q heads 10, 11): warp w merges columns 32w … 32w + 31, reading that band of all 4 partials and their max(S), ΣP: rescale each to the common max, add, divide by ΣP, → bf16 into `o_smem` (Q's SMEM, dead by now). **Store**: the same split, plain 2-byte stores, `o_dmem.at(row / 2, col + (row % 2) · 128)`: warp w writes columns 1280 + 32w … of head 10 and 1408 + 32w … of head 11 of token 1023's row of attn_out, KV head 5's 256 columns, 512 B in all. Then the task returns and its event fires. The 14 padding rows of each m16 tile are merged too but never stored; the O_w values are made up.

Paged Attention Layer
