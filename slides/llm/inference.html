Linear Algebra refresher

Matrix × matrix

A matrix is a grid of numbers. A has n = 2 rows and k = 3 columns: shape (n, k) = (2, 3)

$C = A\,B$: each row of A meets each column of B at the cell they produce

$c_{11}$ = row 1 of A · column 1 of B = 4

$c_{12}$ = row 1 · column 2

Any cell: $c_{ij}$ = row i of A · column j of B

8 cells, 8 dot products of size 3

(n, k) · (k, m) → (n, m): n · m · k = 24 multiply-adds

Cross layout, used again on the attention slides: A to the left of C, B above it, so row i of A and column j of B meet at c_ij. The cost n · m · k is the number the performance part keeps coming back to.

Matrix × vector

A vector is a matrix with one column: x is (k, 1), so this is $C = A\,B$ with m = 1

$y_1 = \sum_{l=1}^{4} a_{1l}\, x_l = 1 \cdot 2 + 0 \cdot 1 + 2 \cdot (-1) + (-1) \cdot 1 = \color{#f5c451}{-1}$

$y_2 = \sum_{l=1}^{4} a_{2l}\, x_l = 0 \cdot 2 + 1 \cdot 1 + 1 \cdot (-1) + 2 \cdot 1 = \color{#f5c451}{2}$

$y_3 = \sum_{l=1}^{4} a_{3l}\, x_l = 3 \cdot 2 + (-1) \cdot 1 + 0 \cdot (-1) + 1 \cdot 1 = \color{#f5c451}{6}$

Same layout, m = 1. Each output is a dot product: this is what q = x W_Q does for every coordinate of q.

Transpose

A column vector a, shape (d, 1) = (4, 1)

Transpose: the column becomes a row. $a^\top$ has shape (1, 4)

$a^\top b$: (1, 4) · (4, 1) → (1, 1). One row times one column is the dot product: $a^\top b = a \cdot b = 6$

For a matrix, entry (i, j) moves to (j, i). $M^\top$: (2, 3) → (3, 2)

The « Matrix version » slide uses Kᵀ: one column per token.

def attention(xs, Wq, Wk, Wv, Wo):
    """xs is the array of x_i"""
    q = xs[-1] @ Wq
    dh = Wq.shape[1]
    s = np.empty(len(xs))
    for i, x in enumerate(xs):
        k = x @ Wk
        s[i] = q @ k / np.sqrt(dh)
    a = np.zeros(len(s))
    for i in range(len(s)):
        a[i] = np.exp(s[i]) / np.sum(np.exp(s))
    z = np.zeros(Wv.shape[1])
    for i, x in enumerate(xs):
        v = x @ Wv
        z = z + a[i] * v
    return z @ Wo

The same equations as the previous slide, for every token at once: stack the n rows x_j into X and every per-token product becomes one matrix product. The mask keeps each token from reading later tokens (j ≤ i), which the per-token sum did by stopping at n. 

def attention(X, Wq, Wk, Wv, Wo):
    """X stacks the n input rows x_i"""
    n, dh = len(X), Wq.shape[1]
    Q = X @ Wq
    K = X @ Wk
    V = X @ Wv
    M = np.zeros((n, n))
    M[np.triu_indices(n, 1)] = -np.inf
    Z = softmax(Q @ K.T / np.sqrt(dh) + M) @ V
    Y = X + Z @ Wo
    return Y

Matrix version

Input: x, n rows of d numbers, one row per token

Query: Q = x · WQ; we follow its last row, q4 (« capital »)

Key: K = x · WK, the same x with another weight matrix

Transpose: KT has one column per token

q4 · k1: row 4 of Q times column 1 of KT

q4 · k2: same row of Q, next column of KT

q4 · k3

q4 · k4: the last token sees every token, itself included

Softmax on row 4: the 4 scores become weights that sum to 1

Value: V = x · WV

Mix: z4 = 0.45 v1 + 0.10 v2 + 0.10 v3 + 0.35 v4, row 4 of A times V

Rows 1 to 3: same steps, all at once; row i only sees rows ≤ i

Output: O = Z · WO, back to n × d


def attention(X, Wq, Wk, Wv, Wo):
    """X: n rows of d numbers, one row per token"""
    n, dh = X.shape[0], Wq.shape[1]
    Q = X @ Wq
    K = X @ Wk
    Kt = K.T
    s = np.zeros(n)
    for j in range(n):
        s[j] = Q[-1] @ Kt[:, j] / np.sqrt(dh)
    a = softmax(s)
    V = X @ Wv
    z = a @ V
    S = Q @ Kt / np.sqrt(dh)
    S[np.triu_indices(n, 1)] = -np.inf
    Z = softmax(S) @ V
    O = Z @ Wo
    return O

Multi-Head Attention

A layer runs H heads side by side, here H = 4. Input x: n × d, with d = H · dh

One product computes Q, K and V: x · [WQ | WK | WV], each W is d × d

Head 1 only uses its column slice of each W: d × dh, as on the previous slide

Regroup the slices by head: head h owns Qh, Kh, Vh, n × dh; the same x feeds them all

Each head computes its own attention Ah = softmax(Qh KhT / √dh + M)

Zh = Ah · Vh, n × dh: Ah to the left, Vh above, as on the previous slide

Side by side, the Zh form Z, n × d

WO is d × d, cut into H row slices of dh rows

Head 1 adds Z1 · WO(1), n × d, to O

Head 2 adds Z2 · WO(2)

Head 3 adds Z3 · WO(3)

Head 4 adds Z4 · WO(4): O = Σh Zh · WO(h) = Z · WO, n × d


def multihead(X, M, Wq, Wk, Wv, Wo, H=4):
    """H heads side by side; d = H * dh"""
    n, d = X.shape
    Q, K, V = X @ Wq, X @ Wk, X @ Wv
    Qh = np.split(Q, H, axis=1)
    Kh = np.split(K, H, axis=1)
    Vh = np.split(V, H, axis=1)
    # head h owns Qh[h], Kh[h], Vh[h]: n x dh each
    A = [softmax(Qh[h] @ Kh[h].T / np.sqrt(d // H) + M) for h in range(H)]
    Zh = [A[h] @ Vh[h] for h in range(H)]
    Z = np.hstack(Zh)
    Wo_h = np.split(Wo, H, axis=0)
    O = np.zeros((n, d))
    for h in range(H):
        O += Zh[h] @ Wo_h[h]
    return O

Up is gated

Input: n rows of d = 2 048 numbers, one row per token

Two blocks read the same x: Gate and Up. Each one outputs a vector of dff = 6 144 numbers

« Paris »: Gate outputs a gate vector, mostly near 0 after SiLU. Up outputs an up vector

Element 2: h2 = gate2 × up2. The gate is closed (≈ 0): h2 ≈ 0

And so on for every element, each one on its own: 6 144 multiplications

What Qwen (and Llama, Mistral, DeepSeek…) actually compute: SwiGLU. Gate on top, the result h in the middle, Up at the bottom, all in the same columns: column j of gate and column j of up give column j of h. The gate is drawn after SiLU, so the dark cells of h are exactly where the gate is closed. 

def ffn(x, Wgate, Wup, Wdown):
    """one row x of X: d = 2048 numbers in, d_ff = 6144 in the middle"""
    g = x @ Wgate
    u = x @ Wup
    h = silu(g) * u   # gate times up, elementwise
    y = x + h @ Wdown
    return y
# weights per layer: 2·d·d_ff (gate, up) + d_ff·d (down) = 37.7M

Same equations three times: one element j of one token i (the sums over k and j are the matrix products written out), one token, then every token at once. Row i of the output only reads row i of the input: no mask, no softmax over tokens. Without SiLU, W_up W_down would collapse into one d × d matrix: the nonlinearity is what makes 6 144 separate rules. 

def ffn(X, Wgate, Wup, Wdown):
    """X: n rows, one per token"""
    G = X @ Wgate
    U = X @ Wup
    H = silu(G) * U   # elementwise: n x d_ff
    Y = X + H @ Wdown
    return Y
# without SiLU, Wup @ Wdown would collapse into one d x d matrix

Numbers: 3 × 2 048 × 6 144 = 37.7 M; attention 2 048 × (2 048 + 1 024 + 1 024) + 2 048 × 2 048 = 12.6 M (8 KV heads). def ffn(X, Wgate, Wup, Wdown):
    """X: n rows of d numbers, one row per token"""
    GU = X @ np.hstack([Wgate, Wup])   # one product: X · [Wgate | Wup]
    G, U = GU[:, :d_ff], GU[:, d_ff:]
    H = silu(G) * U                    # n x d_ff: 3x wider than X
    Y = H @ Wdown                      # back to n x d
    Y += X                             # the residual
    return Y

Prefill, then decode

Prefill: the whole prompt in one pass, n rows at once

It fills the KV cache: k and v of every prompt token, in every block and head

Decode: one token per pass. It reads the cache and appends its own k and v

And again, one pass per token, until the end-of-text token

One prefill pass over the whole prompt fills the KV cache and gives the first token; then one decode pass per token, each reading the cache and appending one k|v pair (gold).

The same layout for « ␣of », n = 5: x, q, the scores, a, z and o are one row. Only k5 and v5 are computed; the cached keys fly from the cache and turn into columns 1–4 of Kᵀ, the cached values fly into rows 1–4 of V. At the end, k5ᵀ and v5 fly back into the cache. 

def decode(x5, Wq, Wk, Wv, Wo, cache):
    """x5: 1 x d, the new token; the cache holds K and V, n-1 rows"""
    q = x5 @ Wq                    # one row
    k = x5 @ Wk                    # only the new key
    Kt = np.hstack([cache.K.T, k.T])   # cached keys: first columns
    s = q @ Kt / np.sqrt(dh)       # 1 x n scores
    a = softmax(s)
    v = x5 @ Wv                    # only the new value
    V = np.vstack([cache.V, v])        # cached values: first rows
    z = a @ V                      # one row
    o = z @ Wo                     # one row
    cache.append(k, v)             # n + 1 rows next time
    return o

Prefill is compute-bound

Abstract model of RTX 5090

A simple machine model, enough to estimate a prefill: - all the model parameters live in GPU memory (VRAM): Llama-2-7B is 13.5 GB of the 32 GB; - VRAM ↔ cache: 1.79 TB/s, read or write (GDDR7, 512 bits × 28 Gb/s); - the cache is infinite: any size, infinite bandwidth. VRAM data is copied there, temporaries are allocated there. So tiling does not matter; - each operation reads its inputs from VRAM once and writes its result to VRAM once (otherwise an infinite cache would keep everything, and only the weights would ever be read); - compute: 209.5 TFLOP/s, bf16 with fp32 accumulation, dense (third-party spec sheets; GeForce cards run fp32 accumulation at half the fp16-accumulation rate). The prompt text and its token ids stay in host RAM: 16 KB, copied once, ignored.

Complexity of matrix product

A is a × b, B is b × c, C is a × c: the two b sides match. 1. The top-left cell of C: row 1 of A against column 1 of B. 2. c11 = a11·b11 + … + a1b·bb1, term by term: each term is 1 multiply + 1 add, so 2b FLOPs per cell. 3. a · c cells, so 2abc FLOPs. 4. Read A and B from VRAM into the cache, once: 2(ab + bc) bytes (bf16: 2 bytes per number). 5. Write C back to VRAM, once: 2ac bytes.

One step, one sequence: 2 FLOPs per weight, ≈ 13.2 GFLOP, plus attention, 4 · L · n · n_h d_h, linear in n (slope 1), not n². The weights dominate up to n ≈ 25 k, the same crossing as in prefill. Grey: the KV cache of a single sequence no longer fits next to the weights (34 k tokens: 18.5 GB / 512 KiB).

Bytes per token vs context size

Every step reads all the weights, 13.2 GB, for one token. And the whole KV cache: 512 KiB per context token, 0.5 GB at n = 1 k. Same shape as the FLOPs: bytes ≈ FLOPs at every n. That is the « 1 FLOP per byte » of the table.

Time per token on 1x RTX 5090

Same rates as for prefill: 1.25 TB/s and 84 TFLOP/s. At n = 1 k: 11 ms of memory for 0.16 ms of compute, 70× apart. ≈ 91 tokens/s, and the tensor cores are idle 98.5 % of the time. The gap is the ratio of the two rates, 84 T / 1.25 T ≈ 67, because decode does ≈ 1 FLOP per byte: it never closes, whatever n.

Batching: B sequences share the weights

Decode B sequences together: their B new rows form a B × d matrix X, and every weight read now serves B rows. Weight products reach B FLOPs per byte. But each sequence attends to its own past: its K and V are its own, read for its single row. Attention stays at 1 FLOP per byte, whatever B. And each sequence's cache takes VRAM: B · n · 512 KiB must fit next to the 13.5 GB of weights.

Throughput vs batch size

Tokens per second for the whole batch, B / time per step. Short contexts: the time per step hardly grows with B (the weights dominate the bytes), so throughput grows ≈ linearly: n = 128 goes from 94 to 6 300 tokens/s. Long contexts: each sequence adds its own cache to read, and the VRAM fills fast: n = 4 k stops at 8 sequences, 326 tokens/s.

Roofline analysis

The prefill roofline, with decode on it. B = 1: every context sits at ≈ 1 FLOP per byte, far left of the ridge (67). Batching moves each curve right, up to the largest B that fits in VRAM: n = 128 reaches the flat part (B = 275, ≈ 115 FLOPs per byte); n = 1 k stops at ≈ 15 (B = 34); n = 4 k at ≈ 4 (B = 8). Key takeaways

Decode is bandwidth-bound

  • Reading the weights dominates at small context size
  • Reading the KV cache dominates at large context sizes
  • It is bandwidth-bound, except for large batch size

Flash-attention: a tiling case study

Real hardware: the cache is finite

Our model had an infinite cache: copy a whole matrix in, compute, write the result back. Real hardware has a finite one: on the RTX 5090, 96 MB of L2 shared by the whole chip, and 128 KB of L1 / shared memory in each SM (streaming multiprocessor: the GPU's core, 170 of them), next to its tensor cores. We keep infinite bandwidth between L2, L1 and the tensor cores. That is still a simplification: on-chip bandwidth is finite too, but at least 10× better than VRAM ⇄ L2, so VRAM stays the bottleneck. A tile must fit in 128 KB: 64 K bf16 numbers, a 256 × 256 block. One Llama-2-7B weight matrix, 4 096 × 4 096, is 256 such blocks. So a kernel reads **parts** of its inputs, a tile at a time, computes what they allow, and moves on. From here on, operations also run one after the other: each one is bound by its own roofline, and the times add up. Cache sizes: TechPowerUp and Cowcotland reports of the GB202 / RTX 5090.

Tiling a matrix product

The same product, four ways to cut C into tiles, one per step. FLOPs never change: 2abc. **1 row**: keep a row of A, stream every column of B; B is read once per row of A: ab + abc. **1 column**: the mirror image: bc + abc. **l × m tiles**: keep l rows of A, stream B by groups of m columns: B is read a / l times, ab + abc / l. Bigger tiles, fewer reads, but they need b(l + m) + lm numbers of cache. The whole matrix as one tile (6 × 12) is our idealized model: every number read once, ab + bc.

Attention: S and A never fit

Area to scale: one layer's S at n = 4 096 (1 GiB) against the L2 (96 MB) and one SM's 128 KB, the green dot. The prefill section counted S and A through VRAM: 8 · nh · n² bytes per layer. On real hardware this is unavoidable as long as softmax is a separate step: it needs the whole row of S before it can normalize it. And the softmax is memory bound (5 FLOPs per 8 bytes): its time adds to the GEMMs'.

FlashAttention-2: chained tiles

FlashAttention-2 chains the three steps inside one kernel. One SM takes a block of Br query rows Qi, then streams K and V tile by tile: Sij = QiKjT lives only in SRAM; the online softmax keeps a running max m and sum ℓ per row and rescales Oi when m grows; Oi += eS − mVj. S and A never reach VRAM. What remains: Q read once, O written once, K and V read once per block of query rows (often less: the L2 shares them between the SMs working on the same head). Bytes per layer through VRAM: without FA2, nh · (8n² + 8n dh); with FA2, nh · (4n dh + 4n² dh / Br). With Br = dh = 128, the n² term halves. The bigger gain is not the bytes but the fusion: one compute-bound kernel, (4dh + 5) FLOPs per 4 bytes ≈ 129 FLOPs per byte, instead of two GEMMs plus a memory-bound softmax (5 FLOPs per 8 bytes). Steps 0–5: the first block of rows, tile by tile. Steps 6–8: each next block plays by itself.

Impact on prefill and decode

Time = Σ over operations of max(FLOPs / 84 T, bytes / 1.25 T), Llama-2-7B, nh = 32, Br = 128. **Prefill**: +7 % at 4 k tokens, +29 % at 32 k, +50 % at 1 M. The untiled softmax was the only memory-bound part of attention; FA2 removes it, and the n² FLOPs stay. **Decode**: ≈ 0 to 2 %. One row per step: S is 1 × n, tiny. Decode's bytes are the weights and the KV cache, which FA2 cannot avoid reading: tiling saves the traffic of intermediate results, not of inputs. Real untiled kernels do worse than this model (fp32 scores, a separate mask), so measured FA2 gains in prefill are larger. Two things this model leaves out. Capacity: without FA, S of one head at 32 k tokens is 2 GiB; long prefills run out of VRAM before they get slow. And reaching the bandwidth: at B = 1, one query row per head gives a naive kernel 32 blocks for 170 SMs; Flash-Decoding splits the KV cache along n across SMs. It saves no bytes, it lets decode run at full bandwidth, which our model assumes.

Key takeaways

LLM optimization is about

  • Tiling computations
  • Chaining tiling computations

Conclusion

  • Inference is prefill + decode
  • Prefill is compute-bound
  • Decode is bandwidth-bound
  • Tiling is a fundamental optimization pattern
